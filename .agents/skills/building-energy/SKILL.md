# building-energy

Prefer an inspected and pinned OpenStudio-MCP deployment for creating OSM geometry and systems; consider LBNL EnergyPlus-MCP for existing IDF workflows. See THIRD_PARTY.md. These integrations are candidates until a real engine run is evidenced. Never report an invented or surrogate simulation as an EnergyPlus result.
Prepare thermal spaces, adjacent surface conditions, constructions, weather/design days, internal gains, schedules, ventilation, infiltration, setpoints and systems. Record assumptions and match geometry to the source. An ideal-load model assesses loads, not a fully specified plant's electricity.
Use upstream capability discovery and bundled workflow skills, not guessed tool names. Save OSM/IDF, engine version, weather hash, run command/tool calls, error logs, SQLite/CSV results and report. Resolve severe/fatal errors; evaluate warnings and unmet hours. Compare a baseline and one controlled variant with identical conditions.
Keep cooling/heating kW, electrical kW, annual kWh and COP distinct. Simulation system topology does not prove spatially routed BIM ductwork/piping. Read output units and sizing conditions before interpreting peaks. Never silently apply ASHRAE baseline templates as Hong Kong course requirements.

For Hong Kong load-design conditions use ../mep-regulations/SKILL.md and docs/HK_HVAC_RULES.md. Keep sourced indoor dry-bulb/humidity and outdoor design conditions separate from annual weather and operating thermostats. The Table 6.4 rule pack does not yet bind actual EnergyPlus sizing objects; a passing standalone check cannot certify the simulation.

For design-day sizing humidity read docs/SIZING_HUMIDITY.md. The explicit optional input writes and audits constant RH sizing schedules and sensible/latent sizing mode in both saved OSM and IDF. It does not add operating humidistats or prove maintained timestep RH; inspect native sizing output and preserve deviations. Annual/PTAC use and complete Hong Kong rule-to-model binding remain pending.

## Repository engine adapter
For the supported synthetic two-adjacent-zone design-day comparison, use `python -m bsa.energy <project.json> --out <new-run> --energyplus <engine.exe>`. Schema example: examples/two-zone-energy/project.json. Restore the pinned Windows x64 tools with scripts/setup_energy.py; see README.md and THIRD_PARTY.md. Inspect analysis.json, OSM/IDF and eplusout.err. This adapter is not a general arbitrary-building or annual-weather pipeline.
The read-only upstream probe is `python scripts/probe_openstudio_mcp.py <generated-model.osm>`. It tests MCP model load and space/zone queries; no upstream simulation execution is claimed. A tool may return isError=false but structured ok=false; treat either failure as failure.

For complete hourly weather years, read docs/ANNUAL_ENERGY.md and use `annual_energy`/`bsa.annual_energy`. Require declared EPW source/station/raw hash, exact calendar coverage, real site derivation, explicit budgets and per-zone unmet-time targets. Preserve hourly/monthly/annual reconciliation and independent lighting balance. Keep supplied thermal loads distinct from lighting electricity and plant input; no invented COP/EUI or net HVAC saving. Inspect completion.json under docs/ENERGY_COMPLETION.md: only the exact inspected executable/source-order limitation can explain initialized false SQL flags, and all other completion facts must pass. Never rewrite native flags or clear failures/unknown exceptions. The example is Chicago TMY3 with synthetic geometry. Actual construction/gains/schedules/weather/HVAC/plant/calibration and domain acceptance remain pending.

For explicit multi-space annual models use examples/annual-energy/three-spaces.json. Require per-space geometry sources and metre-valued boxes. Reject overlap/partial-face contact; inspect reciprocal matching identities/areas and exact hourly zone/light key coverage. Full-face stacked adjacency is supported; arbitrary footprints, partial-face subdivision remain pending; saved box-space binding is supported under docs/THERMAL_BINDING.md.

For saved IFC thermal geometry use `annual_energy_ifc` in examples/thermal-ifc-plan.json or bsa.thermal_binding. Require complete GUID-to-zone mapping, per-space sources and explicit EnergyPlus north-axis angle. The project template must omit geometry/orientation. Read actual saved solid world coordinates; check box corners, boundary triangles, closed winding, face areas and volume, not bounds alone. IFC TrueNorth/georeferencing, constructions, boundaries, schedules and system objects are not automatically imported. Preserve source IFC and bind model/result identities with hashes; generic box space does not establish a real thermal boundary.

For source-declared opaque layers read docs/THERMAL_MATERIALS.md and use examples/thermal-materials-plan.json. Replace the legacy uniform resistance with four sourced role assemblies; never supply both. Require massive-layer physical properties or resistance, plus explicit roughness/optical properties. Verify reopened OSM properties/provenance and reverse the peer interzone layer order. Report layer resistance/conductance without surface films and areal heat capacity separately. Exposed floors remain adiabatic; explicit layers do not prove actual construction, moisture/bridge or product/code applicability.

For weekly gains and simple outdoor air, use examples/thermal-operation-plan.json and docs/THERMAL_OPERATION.md. Require all seven sourced 24-hour fractional profiles, explicit gain splits/occupant activity and fixed scheduled infiltration/ventilation inputs. Reopen and audit saved objects/links/profiles; check exact hourly zone identities and independent lighting/equipment/people/fan integrals. Keep native density-dependent mass flows separate from nominal design volume. This is simple outdoor-air/fan accounting, not a full duct/AHU/plant design or ventilation compliance. Weekly operation is annual-only; do not invent design-day/holiday/seasonal profiles.

For actual fixed-size DX PTAC/electric heat/cycling fan annual analysis, read docs/THERMAL_HVAC.md and use examples/thermal-ptac-plan.json. Require complete sourced zone ratings/flows and five explicit performance curves; disable ideal loads and double-counted PTAC outdoor air. Reopen and audit equipment/curve links and parameters. Preserve native thermal delivery versus DX/heater/fan electricity, hourly/annual component reconciliation and failed unmet-time gates. Positive bounded curves are not product/rated/domain validation; do not infer whole-system electricity from rated COP or certify standard ratings. Spatial IFC equipment/routing and other systems remain pending.

For saved PTAC equipment identity and property-only simulation results read docs/HVAC_DEVICES.md and examples/hvac-equipment-plan.json. Require explicit device/system/space GUID mappings, complete selected unitary-equipment coverage, native body containment and matching saved thermal/flow/efficiency properties. Reopen OSM to verify linked GUIDs; preserve every original IFC entity and source bytes when appending result properties to analysis.ifc. Simulated annual/peak electricity is not nameplate or feeder design power. Preserve failed calculated checks and false design acceptance. Device bounds are not product/clash/port/routing/visual acceptance.

For sourced vertical exterior-wall windows read docs/THERMAL_WINDOWS.md and examples/thermal-windows-plan.json. Require exact Cartesian face/zone, offsets/sill/width/height, geometry source and U/SHGC/visible source. Validate full fit/interzone/overlap only against actual geometry; no placeholder dimensions. Reopen native window geometry/orientation, glazing/source and opaque net areas. Keep film-inclusive simple glazing U distinct from bare opaque-layer conductance. Require complete native hourly solar/heat-gain/loss identities and incident/transmitted bounds; do not infer HVAC electricity/daylight savings or architectural IFC windows from these thermal inputs.

For public-brief concept geometry, scripts/run_public_massing.py emits saved-native geometry-handoff.json using existing thermal extraction and adjacency checks. See docs/CONCEPT_SPACES.md. These are geometric area and WWR targets only; thermal_model_ready=false. Do not infer thermal boundaries, clear air height, glazing properties or simulated results from massing boxes.

Concept handoff window rectangles may use explicit geometry-only thermal_windows.validate(..., require_glazing=False), with no glazing field. This is layout QA only. Formal simulation authoring retains default sourced-glazing validation. Do not invent ratings or treat JSON rectangles as native windows/cut openings; see docs/CONCEPT_SPACES.md.
